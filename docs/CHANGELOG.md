# Changelog

## Purpose

A chronological record of what changed in TransferX — the "what happened, in order" complement to [`IMPLEMENTATION_STATUS.md`](./IMPLEMENTATION_STATUS.md), which answers "what's true right now." See that document's Purpose section for the exact split; don't let the two collapse into duplicates.

## Scope

In scope: user-visible and behaviour-affecting changes (features, fixes, removals), one entry per change.
Out of scope: internal refactors with no behaviour change, minor documentation wording fixes — not everything that happens needs an entry here.

## Format

Follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): most recent changes at the top, grouped under `### Added` / `### Changed` / `### Fixed` / `### Removed`, with unreleased work under `## [Unreleased]`.

Maintained by the [`documentation-standards`](../.claude/skills/documentation-standards/SKILL.md) skill — update it as part of any session that ships a real change, not in a batch after the fact.

## [Unreleased]

### Added
- **A buying club can approach anonymously, and is revealed when the offer is accepted.** Opt-in per offer rather than per club — a club may be open about one target and discreet about another. The seller sees *"A Premier League club"* plus an explicit **Anonymous** marker instead of the name. The *fact* of anonymity is never hidden, only the identity: a seller has to know they are dealing with an undisclosed club even before they know which one. Accepting reveals the buyer; rejection, withdrawal or expiry leaves them permanently undisclosed — that is the point of the feature, not a gap in the reveal.
  - **Masking is server-side and centralised** in the single function every offer response is built through (`_offer_response`). The identity leaks through five fields, not one — the club name, `from_club_id`, `last_actor_club_id`, message `sender_club_id`, and event `actor_club_id` — and the *ids* matter as much as the name, since anyone holding one reads the club straight off `GET /clubs/{id}`. A per-page display guard that missed any of them would make the anonymity fake while looking correct, which is the exact failure mode [ADR 0003](./architecture/decisions/0003-player-status-distinguishes-external-clubs.md) documents.
  - **The competition order book masks anonymous rivals too** (`get_offer_competition`) — it names every club bidding for a player, so masking the offer alone would leak the identity straight out of the panel beside it. `OrderBookClubSummary.id` became nullable rather than carrying a placeholder that looks resolvable but isn't.
  - Six tests, two of which assert the buyer's club id appears **nowhere in the serialised payload** rather than merely that the name is hidden; verified they bite by disabling the mask and watching them fail. Migration `0064` backfills existing offers to non-anonymous, since every approach made before this shipped was made openly. Auction *bids* are a separate model with a separate order book and are unchanged — this covers offers only. (`backend/app/offers/`, `backend/migrations/versions/0064_offer_anonymous_buyer.py`, `frontend/src/lib/buyerIdentity.ts`, `frontend/src/pages/offers/`)

### Changed
- **The War Room's "waiting on you" band is now server-derived.** It previously ran four separate client-side whose-move passes over its own queries. Those queries stay — tiers 2–4 need their rows — but the *verdict* now comes from B2, so the sidebar badge and the band can no longer disagree while both look right. Both consumers share one query key, so the two together still make a single request (verified in the browser: 1 call per page load). `DashboardItem` gained a `deadline` field to make this possible without regressing the band's countdowns; it's the item's own expiry (approval TTL, offer expiry, auction close) and null for deals, which have no per-stage deadline. (`backend/app/dashboard/`, `frontend/src/pages/dashboard/DashboardPage.tsx`)
- **The sidebar now says which sections are waiting on you.** Count badges on Inbox, Deals, Auctions and Approvals, in the same danger red the Notifications badge already uses — so "red in the nav" keeps meaning exactly one thing. Numbers rather than status dots, deliberately: `design_handoff_transferx/CLAUDE.md` rule 10 says colour is never the only carrier of meaning, and a count is its own label. This is the first consumer of the **B2 dashboard aggregate** built earlier in this session and unused until now: `GET /clubs/me/dashboard` already returned each waiting item with a `kind`, which maps 1:1 onto nav destinations, so one request feeds every badge rather than one request per section. Club accounts only — agents and player accounts never call it (verified: zero requests, no 403s). (`frontend/src/components/layout/Sidebar.tsx`, `frontend/src/hooks/useClubDashboard.ts`)
- **Offer Inbox groups competing offers by player, and separates live from finished.** Two clubs bidding for the same player is the strongest card a seller holds, but the inbox rendered it as two unrelated adjacent rows — the ranked order book that compares them already existed on the offer detail page, with nothing pointing to it. Offers are now grouped one row per player: a `2 clubs` chip, both club names, the best fee marked as such, and the row opens the *best* offer, whose detail page carries the order book across every rival. The single "Everything else" bucket — whose own subheading conceded it held "waiting on the other club, or closed" — is split into **In play** (live negotiations plus deals already running) and **Closed** (completed, rejected, withdrawn, expired); for Chelsea's inbox that separates 3 live from 3 finished where previously all 8 rows sat together. The "Your move" band, where offers are actually decided, now warns when rivals exist (*"1 other club is bidding"*), counted across both bands so a rival sitting in "In play" still registers against an offer awaiting your response. A grouped row reports the group's most recent activity rather than the best offer's own date, which can be older than a rival's. (`frontend/src/pages/offers/OfferInboxPage.tsx`)

### Fixed
- **Submitting an offer with the fee left blank returned a 500.** Every field on the offer form except the player is optional, and `OfferCreateRequest.fee_amount` is genuinely nullable — a fee-less offer is legitimate (free transfer, loan, swap). But the D7 approval summaries formatted it as `f"Offer £{body.fee_amount:,.0f}…"`, which raises `TypeError: unsupported format string passed to NoneType.__format__`. Because the summary is built as an *argument* to `approvals_service.maybe_capture`, it raised before any threshold logic ran — so it failed for **every** caller, not just the MANAGER role that check targets. `accept_offer` carried an identical second copy at `router.py:431`, latent only because `counter_offer` guards its assignment (`if fee_amount is not None`) and so can't null a fee back out. Fixed with a `_fee_summary()` helper at both sites, and `maybe_capture` now coerces a null amount to zero rather than reaching `Decimal(None)` — which the summary fix alone would have left exposed for any club with a threshold set. Verified by reverting the fix and watching all three new tests fail with the original `TypeError`. (`backend/app/offers/router.py`, `backend/app/approvals/service.py`)
- **A blank fee and a deliberate free transfer were indistinguishable.** Related to the fix above but a separate defect that outlives it: the form's fee box was silently optional, so "I forgot to type a number" and "there is genuinely no fee" produced identical offers. That also meant a fee-less offer skipped the budget reservation (`create_offer` reserves only `if reserve > 0`) and never escalated for approval (null → 0 → below any threshold) — both correct behaviour for a *real* free transfer, and both wrong for an accidental blank. The fee is now an explicit choice between **Transfer fee** and **No fee**; picking the former and leaving the box empty is rejected client-side, and picking the latter states the intent to the receiving club. (`frontend/src/pages/offers/CreateOfferPage.tsx`)
- **A player under contract to a real-world club showed as "Free agent" when making an offer.** `CreateOfferPage.tsx` read only `player.current_club?.name`, ignoring `world_team` and `team_name` — the same fallback chain `PlayerCard`, `PlayerListRow` and `GlobalSearch` already use, and the fifth site to independently rediscover the gap [ADR 0003](./architecture/decisions/0003-player-status-distinguishes-external-clubs.md) closed at the data layer. A. Abdi (`status: EXTERNAL`, contracted to Nice) now reads "MID · Nice" instead of "MID · Free agent". Making an offer against such a player still creates one with `to_club_id = null`, which no club on the platform can ever accept — flagged, not fixed here, since blocking or reshaping that path is a product decision. (`frontend/src/pages/offers/CreateOfferPage.tsx`)
- **An accepted offer never said what became of it.** `Offer.status` stays `ACCEPTED` for the rest of time — correctly, since the offer *was* accepted and its own lifecycle ended there — but the deal it created can go on to collapse, and `offerStatusVariant` maps `ACCEPTED` to the green `success` badge. Two of the nine accepted offers in the database had collapsed deals, so a dead transfer rendered as a win, in green: the same failure mode as the free-agent badge in [ADR 0003](./architecture/decisions/0003-player-status-distinguishes-external-clubs.md), colour asserting something favourable that isn't true. The remaining in-progress ones were merely useless — "ACCEPTED" is true but the live fact is the stage. `OfferResponse` now embeds the `deal` it produced on both the list and detail endpoints (one query per page via `get_deals_by_offer_ids`, never per row), and a new `offerOutcome()` derives the display state from offer status *and* deal: `Collapsed · at personal terms` in danger, the stage in info while live, `Completed` in green. The offer's own status is demoted to secondary text rather than discarded — it stays the truthful record. Applied to both sides of the trade (Sent Offers and the seller's Inbox), and the offer detail page gained a persistent **View the deal →** link, which previously existed only in the accept mutation's `onSuccess` and vanished as soon as you navigated away. (`backend/app/offers/`, `backend/app/deals/service.py`, `frontend/src/lib/badges.ts`, `frontend/src/pages/offers/`)
- **A resolved listing gave no account of itself.** A closed listing rendered its status as the raw enum `CLOSED` directly beside the sale-*type* badge "Open to Offers" — two labels that flatly contradict each other — with an order book showing nothing but inactive rows. A seller looking at their own sold player could not tell whether an offer had been accepted, the listing had expired unsold, or it had been withdrawn. `GET /sales/{id}` now embeds `active_deal` once a listing is no longer `OPEN` (detail endpoint only, mirroring `fair_value_signal`; player-scoped rather than sale-scoped so it stays correct for listings closed before deals began carrying `sale_id`), and the detail page states the outcome in a sentence — *"An offer from Chelsea was accepted. The transfer is at Paperwork."* — with a link through to the deal. Added `saleStatusLabel()` so statuses read as words rather than enum constants, and the type badge drops its colour once a listing is resolved, so "Open to Offers" stops reading as a live invitation. (`backend/app/sales/`, `frontend/src/pages/market/SaleDetailPage.tsx`, `frontend/src/pages/sales/MySalesPage.tsx`, `frontend/src/components/sales/SaleCard.tsx`, `frontend/src/lib/badges.ts`)

### Fixed
- **7,825 contracted professionals were shown as free agents — and were signable for £0** (audit finding [C5](./DEMO_READINESS_AUDIT.md), [ADR 0003](./architecture/decisions/0003-player-status-distinguishes-external-clubs.md)). `PlayerStatus` had only `CONTRACTED`/`FREE_AGENT`, and `normalize_player_status` derived it from the presence of a **TransferX** contract alone — so every vendor-imported player (essentially the whole 7.9k catalogue) stored as `FREE_AGENT`. Lamine Yamal displayed as "MID · Free agent" while browsable under Barcelona, in the green `success` badge that frames a player as available. Worse, `create_free_agent_deal` gated solely on `status != FREE_AGENT` — a path its own docstring describes as "no seller, no fee, no offer/bid negotiation pipeline" — and with no transfer windows configured, any club user with `MARKET_WRITE` could sign any of them for nothing, instantly, with no counterparty or approval. Added a third status, `EXTERNAL` (contracted to a real-world club that isn't on TransferX): `normalize_player_status` and `vendor/sync.py` now assign it, the signing path rejects it *and* re-derives from the club signals as defence in depth, and buyers see it as "Contracted" (never green) while admin surfaces show all three states distinctly. Migration `0063` adds the enum value and backfills by the same rule — verified 7,825 `EXTERNAL` / 84 `CONTRACTED` / 5 genuinely-unattached `FREE_AGENT`, zero contradictions. The compensating display-layer override in `scouting/service.py` was deleted rather than duplicated — it, and three equivalent frontend guards, had each patched a read path while the write path stayed open. (`backend/app/players/`, `backend/app/vendor/sync.py`, `backend/app/scouting/service.py`, `backend/migrations/versions/0063_player_status_external.py`, `frontend/src/lib/badges.ts`, `frontend/src/types/enums.ts`)
- **Accepting a direct offer made against a listing never closed the listing** — `offers/service.py::accept_offer` created the deal but left the originating sale `OPEN`, and never carried `offer.sale_id` onto `deal.sale_id`. The auction path (`sales/service.py::accept_bid`) had always done both. Consequences: the player kept showing as "Listed" and the listing stayed publicly live while their deal was already in progress — contradicting the deal banner's own "New offers and sale listings are not permitted while a deal is active" — and because `_reopen_sale_after_collapse` keys off `deal.sale_id`, an offer-originated deal could never re-list its sale if it later collapsed. `accept_offer` now sets `deal.sale_id` and closes the listing via a new `sales_service.close_sale_after_offer_accepted()`, which mirrors `accept_bid`'s closing block including releasing and notifying any still-active bidders so no budget is stranded against a dead listing. The Sale state transition deliberately lives in the sales module rather than being written from `offers`. Pinned by three tests: close-on-accept, the collapse→re-list round trip, and a standalone (non-listing) offer regression guard. (`backend/app/offers/service.py`, `backend/app/sales/service.py`)
  - Five existing records were already in this state (Saka, Ødegaard, Caicedo, Gravenberch, Bynoe-Gittens — all `OPEN_TO_OFFERS` listings behind live deals from `AGREEMENT` through `CONFIRMED`). Repaired by `backend/scripts/repair_listings_left_open_after_offer_accepted.py`, which is idempotent, supports `--dry-run`, only touches rows where the deal's own offer provably carries that `sale_id`, and reuses the same service function rather than issuing raw SQL. Deployed and run against Railway 2026-08-12 — verified by direct read-only query rather than by trusting the run's own report: `alembic_version` at `0063`, zero listings `OPEN` behind a live/completed deal. Turned out to be a no-op there: of Railway's 8 offers only 2 were ever made against a listing, and both expired unaccepted, so `accept_offer` never ran there with a `sale_id` present. The assumption recorded here and in `operations/environments-and-deployment.md` — that "Railway carries the same broken rows local did" — was untested when written and turned out to be wrong.
- **Transfer-in-progress banner ran two sentences together and drew the transfer direction backwards** — read as "Chelsea ← Liverpool · Stage: PAPERWORK New offers and sale listings are not permitted…". Split onto its own line and flipped to the natural seller → buyer reading order ("Liverpool → Chelsea"). (`frontend/src/pages/market/PlayerMarketDetailPage.tsx`)
- **Squad position-group "priority gap" verdict was computed from the active filter chip, not the whole squad** — `SquadTable.tsx`'s "X of Y minimum" coverage line and its "No goalkeepers in the squad" empty message were both built from the chip-filtered player list. Clicking "Contract risk" (or any non-"All" chip) filtered every position group down first, so a squad with real depth but no players currently at contract risk read as "0 of 2 minimum — priority gap" across all four positions simultaneously. The verdict now always reflects the full squad regardless of the active filter; only the listed rows respect it, and the empty state distinguishes "genuinely uncovered" from "filtered out." (`frontend/src/components/players/SquadTable.tsx`)
- **Club-name search was undiscoverable, not broken** — `/players/market`'s `club_search` param worked correctly, but the input for it lived inside the collapsed "More filters" accordion while the prominent main search box only ever matched player names. Typing a real club name (e.g. "Arsenal") into the main box silently returned nothing, indistinguishable from a data bug. Moved the club field to always-visible, next to the main search box. (`frontend/src/components/players/PlayerFilters.tsx`)
- **Squad view computed the fair-value model figure but never displayed it** — `SquadTable.tsx`'s "Market vs your valuation" bar only ever compared the legacy `Player.market_value` field (confirmed 0% populated platform-wide — the enrichment job that's supposed to fill it is a no-op with no source configured) against the club's own manually-set `club_valuation`. The real fair-value model amount was already being passed into the row as `fairValue.fair_value` but only ever rendered as a bare confidence label ("HIGH conf.") with no figure attached. Now shows the model amount as the primary comparison value (falling back to legacy `market_value` if that's ever populated, same source order as [ADR 0002](./architecture/decisions/0002-contract-cliff-prefers-fair-value-over-legacy-market-value.md)), relabeled "Model vs your valuation" with confidence folded into the same line. (`frontend/src/components/players/SquadTable.tsx`)
- **80 players across 3 demo clubs had `current_club_id` set with no contract behind it at all** — a violation of the documented invariant that `current_club_id` is only ever derived from an active `Contract` (see [ADR 0001](./architecture/decisions/0001-vendor-data-never-overrides-transferx-contract.md)). Found while investigating the squad-valuation display bug above: Liverpool (29), Chelsea (27), and Arsenal (24) squads were showing real-world rosters with no backing contract, so wage/contract-end/valuation-vs-yours all read blank for most of the squad — at least one player (a real-world Chelsea player) was even misattributed to Liverpool. Backfilled one contract per player through the real `create_contract()` service function (not a raw insert), with a plausible term/wage spread (length weighted 1–5yr, wage scaled off the player's fair-value model score where covered). Two pre-existing contracts with null dates/wage (predating this session) were deliberately left untouched — out of scope. (`backend/scripts/backfill_demo_squad_contracts.py`)

### Fixed
- **Railway's migration chain was broken by a force-push** — a separate audit-remediation branch had been pushed to `origin/main` and applied to Railway's database (migrations `0059`–`0061`), then overwritten locally by a force-push that only had a different, conflicting `0059`. Railway's entrypoint failed on every deploy with `Can't locate revision identified by '0061'`. Recreated matching placeholder migrations for `0059`–`0061` and renumbered the local `vendor_sync_runs` migration to `0062`, chaining after them. (`backend/migrations/versions/0059_transfer_window_association.py`, `0060_deal_fee_disclosed_loan_wage_split.py`, `0061_reaudit_medical_window_grace_option_lock.py`, `0062_vendor_sync_runs.py`)
- **Scheduled jobs never fired at the intended cadence** — APScheduler interval jobs with no explicit `next_run_time` schedule their first execution at `now + interval`, so 24h jobs (`valuation_compute`, `enrichment_sync`, `approval_expiry`, `expire_mandates`, `deal_sla`) and the 6h `client_alerts` job effectively never ran unless the process stayed up for the full interval without a restart. In development the API restarts constantly; in production any deploy or crash resets the clock. Evidence: the latest valuation sat at 2026-07-06 for over a month despite a "daily" recompute. Now every job fires a few seconds after startup via `next_run_time`, and the valuation model immediately improved — HIGH-confidence rows went from 0 to 948 (40.2% of covered players) as the ~12k vendor-sync stat snapshots from the previous session finally reached the model. (`backend/app/main.py`)

### Fixed
- Vendor player-stats sync (API-Football) was completely broken — every sync attempt, success or failure, crashed on a naive/aware datetime mismatch writing `vendor_sync_states` (`DateTime` columns vs. a timezone-aware `datetime.now(timezone.utc)`), so nothing had ever synced successfully. Stripped to naive UTC before assignment, matching the existing convention in `vendor/sync.py`. (`backend/app/stats/service.py`)
- Vendor sync could silently overwrite `team_name` for a player currently under an active TransferX contract, even though `current_club_id`/`Contract` — not `team_name` — is what's actually authoritative and what every view already displays. The stale vendor value would only resurface once the contract lapsed. See [ADR 0001](./architecture/decisions/0001-vendor-data-never-overrides-transferx-contract.md). (`backend/app/vendor/sync.py`)
- A built (Docker `serve -s dist`) frontend bundle silently sent every API request to its own origin instead of the backend — `VITE_API_BASE_URL` resolves to `""` (not `undefined`) when no Docker build-arg is passed, and `??` doesn't treat an empty string as unset. Login looked like it succeeded (`200` from the SPA's own not-found fallback serving `index.html`) but did nothing. Now uses `||`. (`frontend/src/lib/api.ts`)

  - **Roles & capabilities (TRA-151):** four staff roles (`SPORTING_DIRECTOR` and `SCOUT` join `MANAGER`/`READONLY`, migration `0049`) with one static capability matrix in `app/clubs/capabilities.py`; every club write route now carries a capability gate (the old two-router `require_club_write_access` is deleted); previously-ungated writes (offer negotiation messages, squad player edits, player/contract creation) found by the implementation-time re-grep are gated too. New `GET /clubs/me/membership` feeds the frontend's `useClubCapabilities` hook — buttons hide (never disable) by capability, and the sidebar identity shows "Staff: Sporting Director" etc.
  - **Staff deal access (TRA-146):** `is_deal_participant` resolves owner-or-staff, so staff of a participant club see their club's deals, deal room, audit log, medical check, and personal terms — shipped deliberately *after* capability gating (D4), pinned by a regression test asserting READONLY staff get 403 on every deal write.
  - **Role-mapped notifications (TRA-152):** club-directed events fan out per the D5 mapping (deal/offer/bid → owner+SD+manager; scouting/market → +scout; account events → owner only) via `notify_club`/`club_recipient_user_ids`; per-user preference opt-outs still apply per recipient; WS pushes reach all club members.
  - **Team management + invitations (TRA-86):** owner-run Team page (invite by email + role, role changes, removal); invitation tokens sha256-hashed at rest, single-use, 7-day expiry, returned exactly once (dev-friendly copy-link, D6); public `/accept-invite` page creates the staff `User` (explicitly `user_type=CLUB`, D9) and logs them straight in; removal deactivates the user immediately (D10); club-scoped audit events (`STAFF_INVITED/JOINED/ROLE_CHANGED/REMOVED`); migration `0050`.
  - **Spending approvals (Phase 5, D7):** optional per-club `approval_threshold` (owner-set, Finance page) — a MANAGER's money action at/above it returns 202 and lands in a pending-approvals queue (nothing reserved, nothing executed); owner/SD approve (re-validated fresh; stale state lands `APPROVED_FAILED` with reason, both parties notified) or reject; requester can cancel; daily `approval_expiry` job; Approvals page + new `STAFF_INVITATION`/`APPROVAL_REQUESTED`/`APPROVAL_DECIDED` notification types; migration `0051`.
  - **First-run checklists (Phase 6, D8):** per-persona onboarding checklist on the club dashboard, agent pipeline, and player profile — every done-state derived from existing data (zero new endpoints), dismissal in `localStorage`.
  - 57 new backend tests (capability matrix, D4 regression, invitation lifecycle/security, approval flows); backend suite 362 passed; TypeScript clean.

### Fixed
- Deal room was unreachable for an invited agent until after their first negotiation write — `is_deal_participant`'s AGENT branch required an existing `AgentNegotiation` row; now also accepts a live (non-declined) `AgentDealInvitation`. (`backend/app/deals/room_service.py`)
- The mandated agent couldn't advance a deal from `AGENT_NEGOTIATION` to `PERSONAL_TERMS` — `advance_deal` only ever checked for a club profile. Restructured so a staff bypass is checked first, then the mandated-agent case, then the club case. (`backend/app/deals/router.py`, `backend/app/deals/service.py`)
- `PUT /deals/{id}/personal-terms` accepted terms from any agent on the deal, not just the one with the mandate — now checks the caller against `AgentNegotiation.agent_id`. (`backend/app/deals/router.py`)
- A pure staff/admin account (created via `create_superuser.py`, which has no linked club) got a 403 advancing `PAPERWORK → CONFIRMED`, because the club-profile check ran before the staff bypass. Staff bypass is now checked first, unconditionally. (`backend/app/deals/router.py`)
- Agent invitations kept appearing on the agent dashboard ("2 new deal invitations") after the deal had already collapsed or completed. `list_invitations` now joins `Deal` and filters to `IN_PROGRESS`/`PENDING_COMPLETION`. (`backend/app/agents/service.py`)
- Agent commission wasn't recorded unless the agent manually entered an absolute amount alongside the percentage, silently leaving no `AgentCommission` row. `upsert_negotiation_terms` now derives the amount from `commission_pct × agreed_fee` whenever only a percentage is given. (`backend/app/deals/service.py`)
- `AuditEvent.actor_user_id` was populated by no write path and was effectively always null, so the audit log couldn't say who did what. Every deal-mutating service function now threads the caller's user id through; the JSON `GET /deals/{id}/audit-log` endpoint also gained the actor-label resolution the CSV export already had. (`backend/app/deals/service.py`, `backend/app/deals/router.py`, `backend/app/audit/router.py`)
- **TRA-137** — `GET /deals/{id}` required a club profile, so the mandated agent and the transferring player got "Deal not found" opening their own deal. Now resolves any legitimate participant (club/agent/player/staff) via `room_service.is_deal_participant`, and the response hides commission terms from the player (club/agent business, mirroring `AgentNegotiation`'s existing field-scoping). (`backend/app/deals/router.py`)
- **TRA-138** — a club could list any player for sale, or accept a transfer naming itself as seller, with no check that the player was actually registered to them. `POST /sales` and `accept_offer` now validate ownership via a new `players_service.get_owning_club_id` (active contract, falling back to whoever created the player record — the same rule `update_my_club_player` already used). (`backend/app/sales/router.py`, `backend/app/offers/service.py`, `backend/app/players/service.py`)
- **TRA-139** — `GET /sales` and `GET /sales/{id}` leaked `reserve_price`, `best_bid`, and `bid_count` to any unauthenticated or rival-club viewer, defeating the platform's own anonymised order-book design. Now null for everyone except the seller and staff; `minimum_next_bid` stays visible since a bidder needs it to place a valid bid. (`backend/app/sales/router.py`, `backend/app/sales/schemas.py`)
- **TRA-140** — `GET /deals/{id}/medical-check` and `GET /deals/{id}/personal-terms` only required login, so any authenticated user could read any deal's medical status and proposed wages. Now scoped to deal participants. (`backend/app/deals/router.py`)
- **TRA-141** — `GET /deals/{id}/audit-log` and its CSV export had no participant check at all, and the CSV leaked raw actor UUIDs. Now scoped to deal participants, with actor UUIDs resolved to display labels in the export. (`backend/app/audit/router.py`)
- **TRA-127** — any agent could claim an unstarted `AgentNegotiation` and insert themselves into a deal they weren't invited to. `upsert_negotiation_terms` now checks the deal's `AgentDealInvitation` before allowing the first write. (`backend/app/deals/service.py`)
- **TRA-60** — a deal with no mandated agent skipped the `PERSONAL_TERMS` stage entirely, letting a player be transferred without ever consenting to their terms. `advance_deal`'s `AGREEMENT` branch now routes to `PERSONAL_TERMS` for every deal, and the buying club (not just an agent) can propose personal terms when no agent is involved. (`backend/app/deals/service.py`, `backend/app/deals/router.py`)
- Backend test suite was entirely uncollectable — `audit_events.payload_json` used PostgreSQL's `JSONB` type directly, which the SQLite test database can't create. Now `JSON().with_variant(JSONB, "postgresql")`, so Postgres is unaffected and the test suite (243 tests) runs again. (`backend/app/audit/models.py`)

### Changed
- **Personal terms consolidated to a single capture point** (see [ADR 0002](./product/decisions/0002-single-capture-point-for-personal-terms.md)) — previously captured twice (informally during `AGENT_NEGOTIATION`, again at `PERSONAL_TERMS`) with no reconciliation between the two. Now captured exactly once, at `PERSONAL_TERMS`, for both mandated and non-mandated deals, under one consistent account-gated proxy rule (the real player consents if they have an account; the mandated agent proxies only if they don't). `AgentNegotiation` lost its `proposed_wage_weekly`/`proposed_signing_bonus`/`proposed_length_years`/`player_agreement` columns (migration `0047_agent_negotiation_commission_only`); the frontend's `AgentNegotiationWorkspace` lost its player-side panel and `PlayerTermsProposalView` in favour of the existing Personal Terms panel gaining agent-proxy consent buttons. - The Terms card on the deal detail page now shows each club's crest next to its name — `ClubSummary` gained `crest_url` (the underlying club field already existed), and `ClubLink` renders it when passed, opt-in and backward-compatible for every other caller. - The deal timeline now renders the real server-side audit log (`GET /deals/{id}/audit-log`) instead of reconstructing an approximate one from client-side state — every stage advance, negotiation update, clause, instalment, and medical-check change now has a timestamp and an attributed actor.
