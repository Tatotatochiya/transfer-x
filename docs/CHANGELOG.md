# Changelog

## Purpose

A chronological record of what changed in TransferX — the "what happened, in order" complement to [`IMPLEMENTATION_STATUS.md`](./IMPLEMENTATION_STATUS.md), which answers "what's true right now." See that document's Purpose section for the exact split; don't let the two collapse into duplicates.

## Scope

In scope: user-visible and behaviour-affecting changes (features, fixes, removals), one entry per change.
Out of scope: internal refactors with no behaviour change, minor documentation wording fixes — not everything that happens needs an entry here.

## Format

Follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/): most recent changes at the top, grouped under `### Added` / `### Changed` / `### Fixed` / `### Removed`, with unreleased work under `## [Unreleased]`.

Maintained by the [`documentation-standards`](../.claude/skills/documentation-standards/SKILL.md) skill — update it as part of any session that ships a real change, not in a batch after the fact.

## [Unreleased]

### Added
- **Loans now run themselves, and the whole app can see them.** Phase 3 of [`feature_spec/loan-transfers.md`](./feature_spec/loan-transfers.md) — the expiry job, recall, notifications, the read endpoints, and all four UI surfaces. Phases 1–2 made a loan expressible and executable but it could only end by hand, which is why the loan UI was deliberately withheld until now: shipping a button for a feature with no way to finish would have let clubs create loans the platform could not complete.
  - **A daily job returns loans that have reached their end date** and warns both clubs two weeks out. The warning is marked on the loan itself (`ending_soon_notified_at`, migration `0068`) rather than inferred from the notifications table — the first attempt compared a notification's `created_at` against the loan's, two independently-defaulted timestamps, which under SQLite is a datetime-vs-string comparison that never matched, so the job re-warned **every single day** for a fortnight. Its own test caught it.
  - **The parent club can recall a player early** when the terms allowed it (`POST /loans/{id}/recall`). Not window-gated (D8): a loan ending is the agreement running its course, not a new transfer, and blocking it outside a window would strand players at the wrong club. The loanee gets 403, and a loan agreed without a recall option gets 400.
  - **Three read endpoints**, because nothing could display a loan before them: `GET /clubs/me/loans?direction=out|in`, `GET /loans/{id}`, and the loan embedded on player detail. A third club gets **404 rather than 403** on a loan it is not party to — whether a loan exists is not theirs to learn. The list endpoint returns a server-derived `direction` so no consumer re-compares club ids: the same row means different things to the two clubs, one missing a player and one having borrowed him.
  - **Four new notification types** (`LOAN_STARTED`, `LOAN_ENDING_SOON`, `LOAN_ENDED`, `LOAN_RECALLED`), wired through all six touchpoints — the backend enum, migration `0067`, the TS union, the notifications page's labels and colours, and the preferences page, which gains a "Loans" group. Both clubs are told about every event in a loan's life.
  - **The offer form leads with the choice**: permanent transfer or loan, before anything else, because it changes what the rest of the form asks for. A loan asks for dates, an optional loan fee, the wage split, an option to buy, and whether a recall is allowed. **The wage split shows its pound figure live** — clubs agree a percentage but budget in money, so "60%" renders as *"You pay £54,000/wk of £90,000 — his club keeps £36,000/wk"*, and at 100% it says *"the whole of his wage"* rather than claiming his club keeps a remainder that does not exist.
  - **My Club gained an "Out on loan" group** for the parent — player, loanee, return date, what they are paying, any option/obligation, and a two-step Recall. It sits outside the empty-squad branch on purpose: a club can have every player out on loan and an otherwise empty squad, which is exactly when it most needs to see them. On the loanee's side those players appear in the squad with an **"On loan" chip and no open-to-offers toggle** — the server already refuses to let them list or sell a borrowed player, and the UI should not offer to either.
  - **The player market shows "On loan at X until May 2027 · owned by Y".** Public on purpose, and necessary rather than decorative — see below.
  - **Fixed a bug phase 2 introduced:** `CreateOfferPage` addressed every offer to `player.current_club`, which during a loan is the **loanee**. Since `accept_offer` rejects an offer naming a club that does not own the player, an approach for a loaned player could be created but never accepted — failing only at acceptance, with a confusing message. `PlayerDetailResponse` now carries `active_loan`, and the form addresses the parent club.
  - **The deal room's `deal_type` is now fully read-only**, finishing what phase 0 started. The type is fixed when the offer is made; retyping it after acceptance is the original defect this spec exists to fix.
  - Verified live end to end: a £2m loan with a 60% split and a recall option, completed, then all four surfaces checked in a browser and the recall driven through the UI — panel → confirm → loan `RECALLED`, player back in the parent's squad, contracts and wages restored. 10 new tests (30 in `test_loans.py`). (`backend/app/loans/`, `backend/app/players/`, `backend/app/main.py`, `frontend/src/components/players/LoansPanel.tsx`, `frontend/src/pages/offers/CreateOfferPage.tsx`, `frontend/src/pages/club/MyClubPage.tsx`, `frontend/src/pages/market/PlayerMarketDetailPage.tsx`)
- **A loan now actually executes as a loan: the registration moves, ownership does not, and the player can come back.** Phase 2 of [`feature_spec/loan-transfers.md`](./feature_spec/loan-transfers.md), and the point at which the feature stops being a mislabel. Until this, `_complete_deal` never branched on `deal_type` — it deactivated the seller's contract, created one for the buyer, credited the full fee and released the seller's entire wage commitment — so a completed "loan" left the parent club with **no contract, no wage liability and no claim on a player they still owned**, with no return, recall or expiry anywhere in the codebase. Phase 1 blocked that path deliberately; this replaces the block with the real one.
  - **The parent's contract is suspended, not ended**, and its id is recorded on the new `player_loans` row — so the return is a *restore* of the agreement the parent already had, not a new one with a guessed wage and end date. Verified live: a Liverpool player loaned to Chelsea kept his Liverpool contract row intact at `is_active=false` with its real 2028-02-10 expiry, while a Chelsea contract was created ending exactly on the loan's 2027-05-31.
  - **The single-active-contract invariant is preserved rather than relaxed.** `normalize_player_status` resolves the active contract with `scalar_one_or_none()`, so two active rows raise `MultipleResultsFound` — a crash, not a misbehaviour — and that assumption runs through the whole player model. The loanee therefore holds the one active contract (so `current_club_id`, the squad list and the wage bill are all correctly theirs) and the loan row is what answers *who owns him*.
  - **`get_owning_club_id` now returns the parent for the duration**, closing a real hole: it previously returned `current_club_id`, which after a loan completed was the loanee — so **the club a player was on loan at could have listed and sold him**. Verified live: Chelsea, holding the registration, got 400 *"Player is not registered to your club"*; Liverpool, who owned him, created the listing successfully.
  - **The wage splits across both books.** On a 60% split of a £90,000 wage the loanee carries £54,000 and the parent is relieved of exactly that, keeping £36,000 — relief is the *share*, not the parent's whole contract wage, because the parent goes on paying their part. The absolute figure is stored on the loan (`loanee_wage_share`) rather than recomputed from the fraction, so unwinding returns exactly what was taken even if the underlying contract wage differs.
  - **A loan does not trigger a previous owner's sell-on clause.** The permanent path pays one whenever a fee changes hands; doing that on a loan would be a real mispayment to a club that has not been paid anything. Covered by a test.
  - **Selling a player who is out on loan terminates the loan** (D6, decided with the product owner). Blocking the sale would make a loaned player unsellable for up to a year, and letting the new owner inherit the loan is a much larger build. The loanee is unwound first — registration released, wage share released, the parent's retained share released too — and the parent is deliberately *not* restored, because the buyer's contract is about to be created and two active contracts is a state the model cannot represent.
  - **Ending a loan is one function with a reason**, not three code paths: running to term, an early recall and a parent sale all unwind the same finance and the same contracts. Phase 3's expiry job and recall endpoint call the same `end_loan`.
  - **If the parent's contract expired during the loan the player becomes a free agent**, rather than resurrecting a dead contract. This is the single path in the feature that can turn a squad player into one, which is exactly why phase 1's validation refuses a loan that outlasts the parent contract — it is only reachable if the contract is changed mid-loan. Covered by its own test.
  - Migration `0066` creates `player_loans` and the `loanstatus` enum; round-tripped both ways, and the enum is created explicitly with `create_type=False` on the column so `create_table` does not try to emit `CREATE TYPE` twice. 10 new tests, plus a full live run on the dev stack — offer, accept, complete, ownership check — rolled back afterwards. (`backend/app/loans/`, `backend/app/deals/service.py`, `backend/app/players/service.py`, `backend/migrations/versions/0066_player_loans.py`)
- **An offer can now be a loan, chosen at approach time rather than retyped after the seller has accepted.** Phase 1 of [`feature_spec/loan-transfers.md`](./feature_spec/loan-transfers.md). `Offer` gains `deal_type` plus `loan_start`, `loan_end`, `loan_fee`, `wage_split_pct`, `option_to_buy`, `obligation_to_buy` and `recall_allowed`, and `accept_offer` carries all of them onto the `Deal` it creates. Previously it built the `Deal` without passing `deal_type` at all, so **every** offer-originated deal defaulted to `PERMANENT` — a loan could only be expressed by editing the deal room *after* acceptance, meaning the seller agreed to one thing and was then asked to run another. Migration `0065` reuses the existing `dealtype` enum rather than minting a second one with identical members; the downgrade drops the columns and deliberately leaves the enum, since `deals` still uses it (verified by round-tripping the migration).
  - **The wage split is a fraction, 0.0–1.0**, matching `sell_on_pct` and `agent_commission_pct` rather than introducing a third convention — see the standing gotcha that `commission_pct` is a fraction, not a percentage. Null means the loanee pays the whole wage.
  - **`agreed_fee` mirrors `loan_fee` on a loan deal** rather than being left at zero. Deliberate duplication: `collapse_deal` releases against `agreed_fee`, D7 approval thresholds test against it, and agent commission is a share of it — all three would silently read zero for a loan otherwise. `_complete_deal` already preferred `loan_fee` when set, so both now resolve to the same number.
  - **`deal_type` is not counterable.** Loan *terms* are negotiable through `PATCH /offers/{id}/counter`; the type is not. Countering a loan with a permanent offer is a different proposal, and allowing the swap would make the deal's own audit trail incoherent.
  - **Loan validation is enforced twice**, in the request schema and again in `offers/service.validate_offer_terms`, because `create_offer` is callable from paths that never construct an `OfferCreateRequest`. Rules: a loan needs both dates and must end after it starts; ≤ 18 months; `wage_split_pct` within 0–1; a loan carries no `fee_amount` and a permanent carries no loan terms; an obligation to buy needs a price. And **a loan may not outlast the player's parent contract** — without that rule the phase-3 return path would find an expired contract and correctly, but very surprisingly, turn a squad player into a free agent. A null contract end date skips the check rather than blocking.
  - **`FREE_TRANSFER` and `PRE_CONTRACT` are rejected as offer types** (422). They are derived by the free-agent and pre-contract signing paths in `players/service.py`, never proposed by a club.
  - **Loan deals cannot complete yet, by design.** `_complete_deal` raises for a `LOAN` and names phase 2. Everything in that function permanently transfers the player — it deactivates the seller's contract, creates one for the buyer, credits the full fee and releases the seller's whole wage commitment — and for a loan the result is irreversible: the parent club would be left with no contract and no claim on a player they still own. A loan can be proposed, negotiated and agreed; it cannot execute until the mechanics exist. The guard is removed in the same commit that adds the branch. **The offer-form loan toggle is deliberately not built yet** for the same reason.
  - Verified live on the dev stack: a loan offer at £2m with a 60% split on a £90k wage reserved exactly £2,000,000 and £54,000; withdrawing it returned both to zero; and all four rejection paths returned 400 with their specific messages, including the contract-expiry one naming the date. 16 new tests. (`backend/app/offers/`, `backend/app/deals/`, `backend/migrations/versions/0065_offer_deal_type_and_loan_terms.py`)
- **Offers now reserve wage budget, not just transfer budget.** Independent of loans and older than them: `reserve_budget` has always taken a `wage_weekly` argument with a real affordability check behind it (`clubs/service.py:414`), and **not one of the six budget calls in the offers module ever passed one**. A club could commit to wages it had no room for and only discover it at completion, where `_complete_deal` adds the wage regardless — so the check existed and could never fire. Reserve, counter, improve, accept and release now all carry both figures, and a new `Offer.reserved_wage_weekly` column records what was taken so a withdrawal gives back exactly that. **This tightens validation on existing permanent offers**: a club with a full wage bill will now be refused an offer it could previously send, which is correct but is a behaviour change, not a silent fix.
  - **Found, not fixed:** when the *seller* counters at a higher fee, the buyer's reservation is not recomputed — `counter_offer` only adjusts it when the buyer is the actor — so accepting a raised counter commits the original, lower figure while the deal records the higher `agreed_fee`. Pre-existing, and now applies to the wage half too. Left alone because the fix needs a product call: refusing an acceptance the buyer can no longer afford is a real behaviour change, not a bug fix. (`backend/app/offers/service.py`, `backend/app/clubs/service.py`)
- **A buying club can approach anonymously, and is revealed when the offer is accepted.** Opt-in per offer rather than per club — a club may be open about one target and discreet about another. The seller sees *"A Premier League club"* plus an explicit **Anonymous** marker instead of the name. The *fact* of anonymity is never hidden, only the identity: a seller has to know they are dealing with an undisclosed club even before they know which one. Accepting reveals the buyer; rejection, withdrawal or expiry leaves them permanently undisclosed — that is the point of the feature, not a gap in the reveal.
  - **Masking is server-side and centralised** in the single function every offer response is built through (`_offer_response`). The identity leaks through five fields, not one — the club name, `from_club_id`, `last_actor_club_id`, message `sender_club_id`, and event `actor_club_id` — and the *ids* matter as much as the name, since anyone holding one reads the club straight off `GET /clubs/{id}`. A per-page display guard that missed any of them would make the anonymity fake while looking correct, which is the exact failure mode [ADR 0003](./architecture/decisions/0003-player-status-distinguishes-external-clubs.md) documents.
  - **The competition order book masks anonymous rivals too** (`get_offer_competition`) — it names every club bidding for a player, so masking the offer alone would leak the identity straight out of the panel beside it. `OrderBookClubSummary.id` became nullable rather than carrying a placeholder that looks resolvable but isn't.
  - Six tests, two of which assert the buyer's club id appears **nowhere in the serialised payload** rather than merely that the name is hidden; verified they bite by disabling the mask and watching them fail. Migration `0064` backfills existing offers to non-anonymous, since every approach made before this shipped was made openly. Auction *bids* are a separate model with a separate order book and are unchanged — this covers offers only. (`backend/app/offers/`, `backend/migrations/versions/0064_offer_anonymous_buyer.py`, `frontend/src/lib/buyerIdentity.ts`, `frontend/src/pages/offers/`)

### Changed
- **The player market's "asking vs fair value" cell was empty on every row, for every player, always — and so were two other features reading the same field.** The batch valuation endpoint built each response as `build_valuation_response(row)` with no `reference_price`, and that argument is the only thing that makes `service.py:163` compute a divergence. So `divergence` came back `null` for all 7,914 players. `PlayerListRow` opened with `if (!signal?.divergence) return null` and threw the entire cell away — including the model's fair value, which was sitting unread in the same payload. The market page's **"Best value first" sort chip was a no-op** (every comparand fell back to `Infinity`, so the comparator was `Infinity - Infinity` = `NaN` for every pair) and its **"Under fair value" stat card was pinned to 0**. The grid view was unaffected throughout, because `FairValueBadge` renders `Model £Xm` whether or not a divergence exists — the same search showed figures as cards and nothing as rows.
  - **Server-side fix:** the batch now resolves a reference price per player — an open non-auction listing's `asking_price`, else the legacy `Player.market_value` — in one extra query for the whole page, never one per row. D7 is honoured exactly: auctions are excluded, so the batch cannot surface a divergence the sale detail endpoint deliberately withholds. The spec had specified the batch as carrying no divergence at all; the frontend was built against the opposite assumption in three places, so `docs/feature_spec/fair-value-vs-asking-signal.md` is amended rather than the frontend bent to match. A test asserting `divergence is None` with the comment *"batch never carries divergence"* was encoding the gap as intent — replaced, plus three new tests covering fixed-price, the auction exclusion and the `market_value` fallback.
  - **The cell now matches the squad table:** two aligned rows, `model` over `asking`, labels in a fixed 46px column so the figures form a column you can scan. Verified live against real data at 1280/900/420px — a constant **170×20px** model-only, **170×40px** with an asking price, no wrapping and no page overflow at any width. All 36 rows of a real search view now carry a figure where every one previously read "No signal".
  - **The model leads here, and that is the whole point of the shape.** ~30% of players carry a model valuation (2,359 of 7,914, verified) and **0% carry `market_value`**, the field this cell labelled "asking" — so "Asking vs fair value" was comparing a number that usually exists against one that never does, and bailing when the second was missing. The 14px/600 weight goes to whichever figure answers *what would he cost* — the asking price where there is one, the model otherwise — so the cell always carries exactly one value-sized figure, the same rule as the squad cell. Unlike the squad's "yours", the asking row is simply absent when there is none: you cannot set another club's price, so an empty row would be inert rather than an invitation.
  - **Colour is directional here, the opposite call from the squad cell's magnitude banding**, and deliberately so: that cell compares a club's own book value against the model, where above and below are both merely facts; this one is somebody else's asking price seen by a buyer, where below-model is genuinely good news. It reuses `FairValueBadge`'s exported `BAND_COLOUR`/`BAND_PHRASE` rather than re-deriving them — deleting a private copy that had drifted into its own three-way banding and broke D5's copy rule by saying "fair value" where the rule is always "model". Verified per band: `WELL_ABOVE` danger red, `ABOVE` amber, `IN_LINE` muted, `BELOW`/`WELL_BELOW` green with the row's bargain ring firing on exactly those two.
  - The 8px bar came out rather than being restyled: it was `style={{ width: "50%" }}`, hardcoded, encoding nothing since the day it shipped.
  - **`OPEN_TO_OFFERS` listings now carry divergence too**, reversing spec line 382 with the product owner. That exclusion was semantic — a guide price is not a firm one — rather than the confidentiality concern behind D7, and an `OPEN_TO_OFFERS` asking price is already published on the listing exactly as a fixed price is. D7 itself is untouched and now reads as what it always said: **`AUCTION` is the only excluded type**, because a reserve and the bid figures are the seller-side numbers that are actually hidden (TRA-139). The change had to move in **both** endpoints — the batch *and* the sale-detail embed — or a market row reading "▲190%" would have linked through to a sale page showing no divergence at all, which is the same class of contradiction this entry started out fixing.
  - Verified live on the dev stack after the change: R. Calafiori £16.8m asking vs £14.9m model → `+12.8% ABOVE`; A. Garnacho £31.0m vs £10.7m → `+189.7% WELL_ABOVE`; the one open `AUCTION` still returns `divergence: null` on both endpoints. Garnacho's row renders `model £10.7m / asking £31.0m ▲ 190%` in danger red at a constant 170×40px with no overflow at 1280px or 420px — a three-digit percentage was the widest chip the cell had to hold.
  - **The sale-detail embed's own `market_value` fallback didn't exist, despite the batch's docstring already claiming "source order matches `sales/router.py`."** `asking_price` is optional at creation for every sale type — nothing requires a club to set one outside `AUCTION`'s deadline — so a `FIXED_PRICE` or `OPEN_TO_OFFERS` listing with none set is a reachable gap, not a hypothetical: `GET /sales/{id}` computed `reference = sale.asking_price` with no fallback, so that listing's page showed no divergence even when the same player's `market_value` would have produced one in the market list — the identical "batch and detail disagree" failure mode as the `OPEN_TO_OFFERS` fix directly above, in a second dimension. Now `sale.player.market_value` (already eagerly loaded via `selectinload`) is used whenever `asking_price` is unset, for any non-auction type; an auction still never falls back, verified with a dedicated test setting `market_value` on an auctioned player and asserting `divergence` stays `null`. Verified live: seeded a real player's `market_value` to £55m, listed him `FIXED_PRICE` with no `asking_price`, confirmed the sale page returned `£55,000,000 WELL_ABOVE` against his £10.6m model figure, then withdrew the sale and cleared the seeded value.
  - **Still worth knowing:** `market_value` remains 0% populated on real data, so both fallbacks stay inert in practice and every divergence today still comes from the two open non-auction listings with an explicit asking price. Separately, `players/service.py`'s server-side `sort_by=value` orders by `fair_value - Player.market_value` and is dead for that same reason — unused by the frontend today, and B3's to fix. (`backend/app/valuation/{service,router}.py`, `backend/app/sales/router.py`, `frontend/src/components/players/{PlayerListRow,FairValueBadge}.tsx`, `docs/feature_spec/fair-value-vs-asking-signal.md`)
- **The squad's valuation cell now shows the model's figure on every row, with the club's own beneath it.** Reported as taking too much space while its text stayed too small to read — both true, and one cause: the cell was built to a single fixed shape (`SCREENS.md:230` — an 11px label, a 6px two-segment bar, 12px muted figures) whether or not it had anything to compare. `club_valuation` is only ever written by hand through `PATCH /clubs/me/players/{id}` and is seeded nowhere, so on a squad nobody has valued, **every row rendered an empty grey bar** — both segments are skipped when either figure is missing — over the words "— model · set yours". Measured at 1280px that cost **382px of width** (it was the only `flex-1` cell besides the player's name, so it absorbed all the row's slack) and 47px of height to say nothing; on a tablet its label wrapped and the row grew to **79px**.
  - Now two aligned rows — `model` over `yours`, labels in a fixed 38px column so the figures line up as a column you can scan down the squad. Every state is a constant **170×40px** from 768px to 1280px, against 190–382px wide and 47–79px tall before.
  - **The model row renders even when there is no model figure**, because that absence is information rather than a hole: `valuation/service.py:51` refuses a row for a player under `MIN_MINUTES` (450, ≈ 5 full matches), with no position, or with no vendor stats — "Ineligible players get no row at all — never a made-up number". A dash there reads as fringe, injured or newly signed, and its tooltip says so. Roughly 70% of players are in that state today, so hiding the row would have made the model look broken on most of the squad.
  - **The figures moved up to 14px/600 `text-text`**, matching the Contract ends and Wage / wk cells beside them, and that weight goes to whichever figure is the club's best answer — its own valuation where one exists, the model's otherwise — so the cell always carries exactly one value-sized figure like its neighbours. Previously both money values sat at 12px muted, the smallest and lowest-contrast text in the row, beneath an 11px label that was the longest string in the cell: the label read louder than the data it described.
  - **The bar was removed rather than restyled.** Its two segments are `min/max` and `|v−m|/max` of the same denominator, so they always sum to exactly 100%: the length was constant and only the split point moved, encoding nothing the signed percentage beside it did not already state more precisely, for the price of a full line.
  - **Colour now tracks the size of the gap, not its direction** — neutral under ±25/30%, amber beyond, with ▲/▼ carrying direction (rule 10). The old cell painted any positive divergence green, which reads as a verdict on the club's own book value; for a player you already own, carrying him above or below the model are both merely facts, and D5's copy rule is that the model never renders one. Deliberately *not* `FairValueBadge`'s mapping, which is a buyer's view of someone else's asking price and correctly treats "above model" as a warning. Thresholds are ported from `backend/app/valuation/constants.py` so a gap computed in the browser lands in the band the API would have given it (−10..+10 in line, ≤−25 or ≥+30 wide).
  - Editing gained a visible affordance — a dotted underline in accent, rather than muted text distinguishable only on hover, which a touch device never gets — and the input carries the model's figure as its placeholder so there is a number to anchor to. New `formatCompactCurrency`: `formatCurrency`'s full precision is a single unbreakable token and is what overflowed the tier-2 cards fixed earlier this session.
  - **Not fixed, and worth a decision:** the "set yours" affordance is deliberately 13px text rather than a rule-6-compliant 44px button, because a button added 26px of height to the *majority* of rows and would have been the only compliant control in a table whose open-to-offers toggle is 20×36px — touch targets here need one table-wide decision, not a single compliant outlier. And the cell is still `hidden md:block`, so a phone can neither see nor set a valuation, though `SCREENS.md:236` says it should drop to a second line rather than disappear. (`frontend/src/components/players/SquadTable.tsx`, `frontend/src/lib/utils.ts`)
- **The War Room's "waiting on you" band is now server-derived.** It previously ran four separate client-side whose-move passes over its own queries. Those queries stay — tiers 2–4 need their rows — but the *verdict* now comes from B2, so the sidebar badge and the band can no longer disagree while both look right. Both consumers share one query key, so the two together still make a single request (verified in the browser: 1 call per page load). `DashboardItem` gained a `deadline` field to make this possible without regressing the band's countdowns; it's the item's own expiry (approval TTL, offer expiry, auction close) and null for deals, which have no per-stage deadline. (`backend/app/dashboard/`, `frontend/src/pages/dashboard/DashboardPage.tsx`)
- **The sidebar now says which sections are waiting on you.** Count badges on Inbox, Deals, Auctions and Approvals, in the same danger red the Notifications badge already uses — so "red in the nav" keeps meaning exactly one thing. Numbers rather than status dots, deliberately: `design_handoff_transferx/CLAUDE.md` rule 10 says colour is never the only carrier of meaning, and a count is its own label. This is the first consumer of the **B2 dashboard aggregate** built earlier in this session and unused until now: `GET /clubs/me/dashboard` already returned each waiting item with a `kind`, which maps 1:1 onto nav destinations, so one request feeds every badge rather than one request per section. Club accounts only — agents and player accounts never call it (verified: zero requests, no 403s). (`frontend/src/components/layout/Sidebar.tsx`, `frontend/src/hooks/useClubDashboard.ts`)
- **Offer Inbox groups competing offers by player, and separates live from finished.** Two clubs bidding for the same player is the strongest card a seller holds, but the inbox rendered it as two unrelated adjacent rows — the ranked order book that compares them already existed on the offer detail page, with nothing pointing to it. - **Railway's migration chain was broken by a force-push** — a separate audit-remediation branch had been pushed to `origin/main` and applied to Railway's database (migrations `0059`–`0061`), then overwritten locally by a force-push that only had a different, conflicting `0059`. Railway's entrypoint failed on every deploy with `Can't locate revision identified by '0061'`. Recreated matching placeholder migrations for `0059`–`0061` and renumbered the local `vendor_sync_runs` migration to `0062`, chaining after them. (`backend/migrations/versions/0059_transfer_window_association.py`, `0060_deal_fee_disclosed_loan_wage_split.py`, `0061_reaudit_medical_window_grace_option_lock.py`, `0062_vendor_sync_runs.py`)
- **Scheduled jobs never fired at the intended cadence** — APScheduler interval jobs with no explicit `next_run_time` schedule their first execution at `now + interval`, so 24h jobs (`valuation_compute`, `enrichment_sync`, `approval_expiry`, `expire_mandates`, `deal_sla`) and the 6h `client_alerts` job effectively never ran unless the process stayed up for the full interval without a restart. In development the API restarts constantly; in production any deploy or crash resets the clock. Evidence: the latest valuation sat at 2026-07-06 for over a month despite a "daily" recompute. Now every job fires a few seconds after startup via `next_run_time`, and the valuation model immediately improved — HIGH-confidence rows went from 0 to 948 (40.2% of covered players) as the ~12k vendor-sync stat snapshots from the previous session finally reached the model. (`backend/app/main.py`)

### Fixed
- Vendor player-stats sync (API-Football) was completely broken — every sync attempt, success or failure, crashed on a naive/aware datetime mismatch writing `vendor_sync_states` (`DateTime` columns vs. a timezone-aware `datetime.now(timezone.utc)`), so nothing had ever synced successfully. Stripped to naive UTC before assignment, matching the existing convention in `vendor/sync.py`. (`backend/app/stats/service.py`)
- Vendor sync could silently overwrite `team_name` for a player currently under an active TransferX contract, even though `current_club_id`/`Contract` — not `team_name` — is what's actually authoritative and what every view already displays. The stale vendor value would only resurface once the contract lapsed. See [ADR 0001](./architecture/decisions/0001-vendor-data-never-overrides-transferx-contract.md). (`backend/app/vendor/sync.py`)
- A built (Docker `serve -s dist`) frontend bundle silently sent every API request to its own origin instead of the backend — `VITE_API_BASE_URL` resolves to `""` (not `undefined`) when no Docker build-arg is passed, and `??` doesn't treat an empty string as unset. Login looked like it succeeded (`200` from the SPA's own not-found fallback serving `index.html`) but did nothing. Now uses `||`. (`frontend/src/lib/api.ts`)

  - **Roles & capabilities (TRA-151):** four staff roles (`SPORTING_DIRECTOR` and `SCOUT` join `MANAGER`/`READONLY`, migration `0049`) with one static capability matrix in `app/clubs/capabilities.py`; every club write route now carries a capability gate (the old two-router `require_club_write_access` is deleted); previously-ungated writes (offer negotiation messages, squad player edits, player/contract creation) found by the implementation-time re-grep are gated too. ### Fixed

- A pure staff/admin account (created via `create_superuser.py`, which has no linked club) got a 403 advancing `PAPERWORK → CONFIRMED`, because the club-profile check ran before the staff bypass. Staff bypass is now checked first, unconditionally. (`backend/app/deals/router.py`)
- Agent invitations kept appearing on the agent dashboard ("2 new deal invitations") after the deal had already collapsed or completed. `list_invitations` now joins `Deal` and filters to `IN_PROGRESS`/`PENDING_COMPLETION`. (`backend/app/agents/service.py`)
- Agent commission wasn't recorded unless the agent manually entered an absolute amount alongside the percentage, silently leaving no `AgentCommission` row. `upsert_negotiation_terms` now derives the amount from `commission_pct × agreed_fee` whenever only a percentage is given. - `AuditEvent.actor_user_id` was populated by no write path and was effectively always null, so the audit log couldn't say who did what. Every deal-mutating service function now threads the caller's user id through; the JSON `GET /deals/{id}/audit-log` endpoint also gained the actor-label resolution the CSV export already had. (`backend/app/deals/service.py`, `backend/app/deals/router.py`, `backend/app/audit/router.py`)
- **TRA-137** — `GET /deals/{id}` required a club profile, so the mandated agent and the transferring player got "Deal not found" opening their own deal. - **TRA-138** — a club could list any player for sale, or accept a transfer naming itself as seller, with no check that the player was actually registered to them. `POST /sales` and `accept_offer` now validate ownership via a new `players_service.get_owning_club_id` (active contract, falling back to whoever created the player record — the same rule `update_my_club_player` already used). - **TRA-140** — `GET /deals/{id}/medical-check` and `GET /deals/{id}/personal-terms` only required login, so any authenticated user could read any deal's medical status and proposed wages. Now scoped to deal participants. (`backend/app/deals/router.py`)
